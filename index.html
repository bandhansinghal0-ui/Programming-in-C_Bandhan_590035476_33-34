06 / CampusGuard case study

How the system is designed.

CampusGuard combines a campus graph, emergency state, route calculation, reporting permissions and incident records inside a console-based C application.

01 / PROBLEM

Emergency information can change quickly

A route that is normally shortest may become unsuitable when a location, road or exit is reported as unsafe. CampusGuard models this changing state and recalculates navigation.

02 / CAMPUS MODEL

Graph-based network

The prototype represents 29 named campus locations as nodes connected by weighted roads. Three nodes are designated as emergency exits.

03 / ROUTING

Dynamic exit comparison

The routing engine evaluates available exits, ignores blocked or hazardous nodes, and recommends the shortest currently available route.

04 / ACCESSIBILITY

Accessibility-aware navigation

Road connections store accessibility information, allowing the route calculation to skip connections that are not marked accessible when mobility assistance is required.

05 / PERMISSIONS

Guest reports, admin verification

Users can report roads, hazards and exit problems. Reports are treated cautiously in navigation, while the admin control room can confirm, reject, clear or reopen resources.

06 / PREPAREDNESS

More than route finding

The project also includes SOS and person reports, roll call, safety instructions, drill mode, readiness checks, incident history, statistics and project-level simulation tools.

07 / Explore the complete project

Inside CampusGuard

CampusGuard is more than one routing screen. Explore the major modules, emergency workflow, user/admin responsibilities, C programming concepts and preparedness features designed into the prototype.

PROJECT EXPLORER
01 / NAVIGATIONDynamic emergency routing

Compares all three emergency exits and selects the shortest currently usable path through the 29-location campus graph.

02 / HAZARDSHazard-aware decisions

Reported unsafe locations can be excluded from route calculation so the recommended path can adapt when campus conditions change.

03 / ROADSRoad status reporting

Road problems can be reported and reviewed, allowing route availability to change rather than assuming every connection is always safe.

04 / EXITSExit availability

Exit issues can be reported and the system can compare alternatives instead of depending on one fixed evacuation exit.

05 / ACCESSIBILITYAccessible route mode

Connections store accessibility information, enabling mobility-aware route calculation that avoids links not marked accessible.

06 / RESPONSESOS & person reporting

The response layer includes SOS/person reports so the project covers assistance and accountability as well as navigation.

07 / RECORDSIncident history

Incident records can be stored, searched and reviewed, creating a trace of simulated emergency activity and response information.

08 / INSIGHTSStatistics

Project-level statistics summarize recorded activity, helping turn stored incident data into a more useful operational view.

09 / SIMULATIONDrills & simulations

Preparedness tools allow emergency scenarios to be practiced without presenting the student prototype as a real emergency service.

STEP 01Emergency or hazard is identified
STEP 02User selects location and situation
STEP 03Campus state and restrictions are evaluated

The workflow demonstrates the logic of the academic prototype; real emergencies must follow official campus/emergency procedures.

GUEST / USERReport what is happening

Submit hazard, road and exit reports; request route guidance; use accessibility-aware navigation; and simulate SOS/person reporting.

CONTROL ROOMVerify changing conditions

Administrative controls can confirm, reject, clear or reopen reported resources so temporary reports do not permanently alter the network.

DESIGN IDEASeparate reporting from verification

The project distinguishes a user's report from an administrator's verification, reflecting the need to treat unverified information cautiously.

DRILL MODEPractice scenarios

Run simulated emergency conditions to demonstrate system behavior without implying a real emergency has occurred.

Roll-call functionality supports the broader idea of checking people during a simulated response.

GUIDANCESafety instructions

Safety information complements routing so the prototype is not limited to simply calculating a path.

READINESSReadiness checks

Preparedness checks help represent the preventive side of emergency management, not only reaction after an incident.

15 / Behind the Project

How the C project is structured

Graph model

Locations are nodes and roads are weighted connections used for route calculations.

Arrays & strings

Store campus data, codes, report information and application state.

Functions

Separate navigation, reporting, searching, statistics and control-room behavior.

Conditional logic

Evaluates hazards, exit state, accessibility and report status.

File handling

The console project uses persistent records for incident/history concepts.

User/Admin thinking

Reporting and verification are separated to model different permissions.

INPUT → campus condition\nMODEL → 29-node network\nCHECK → hazards + roads + exits + accessibility\nCOMPARE → available emergency exits\nOUTPUT → route + response information\nRECORD → incident history + statistics
CampusGuard is a student-built academic prototype and browser simulation. It is not an official UPES emergency system and must not be relied on during a real emergency.
